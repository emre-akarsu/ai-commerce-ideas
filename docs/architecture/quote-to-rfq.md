# Quote to RFQ: sending a saved quote's supplier messages through the approval flow (design note, 2026-10-07)

Plan: `docs/product/10-roadmap-to-functional-app.md` stages 3.1 and 3.2. Status: **implemented** (2026-10-07) after the seam below was added: `PurchasingService.prepare_text_rfq` / `check_text_rfq` / `list_text_rfqs` (`service.py`, `service_port.py`), `employees/purchasing/rfq_from_quote.py`, `apps/api/quote_rfq_routes.py`. Tests: `tests/pack/test_text_rfq.py`, `tests/api/test_quote_rfq.py`.

## What exists
* `components.pricebook.rfq_messages.draft_rfq_messages` renders templated drafts per supplier: `per_supplier` (one message, all of that supplier's lines) or `per_item`. Line text is refused (never repaired) if it holds a link, address, markup, braces or control characters. The result is data (`draft_not_sent`). `apps/api/quote_service.py` already exposes these inside `price-books-ui/1`.
* The send path: `PurchasingService.prepare_rfqs(ctx, request_id, vendor_ids, candidate_mpns)` builds an `RFQ`, adds the business identity block (`_business_identity`), asks `SendService.prepare` for a `PreparedMessage` (footer, `mime_hash`) and appends `rfq.prepared`. `approve_send(ctx, rfq_id, mime_hash)` compares the hash with the held prepared message, issues a per-message `Approval` bound to that hash, moves the request through `Workflow` (events) and calls `SendService.send`, which verifies the approval and the hash.
* Rule R1 therefore already holds: editing any byte changes `mime_hash`, the approval does not match, and the transport is only reachable inside the send-service.

## Why the current flow cannot carry the aggregated message
1. **The body is not an input.** `prepare_rfqs` takes vendor ids and candidate MPNs only. The text is produced inside the service by the private `_rfq_body(request, vendor, candidates, settings)` ("Please quote the following part(s): - MPN (manufacturer)", one `Request.quantity`). There is no public method that accepts a subject and body, so the `rfq_messages` text cannot reach the prepared message.
2. **One request is one part.** `Request` has one `family`, one `quantity`, one `attributes` set, and `RFQ.candidate_mpns` must be Tier A/B candidates of that request (`_rfq_mpns` refuses anything else: R2, R3). A quote line (a kit line, free buyer wording, with a quantity and unit) is not a candidate part. Creating one `Request` per line and calling `prepare_rfqs` would (a) not use the templates, (b) produce one message per line per supplier, i.e. only the `per_item` shape and with the wrong text, and (c) fail for lines that have no identified candidate.
3. **Vendor ids differ.** `rfq_messages` are keyed by price-book `merchant_id`; `prepare_rfqs` needs a `Vendor` that is preferred, attested and not suppressed (`check_supplier_guards`, callback-pending, contact verification). A merchant to vendor mapping, owned by the tenant, is needed and must refuse a merchant with no verified vendor.

Reaching around this (calling `svc._send`, `svc._prepared`, `svc._approvals` from a new module) would duplicate `approve_send` and bypass its guards, so it is not an option. Editing `service.py` is outside this ticket (another agent is changing its store wiring).

## Proposed mapping (no change to `domain.py` or `ports.py`)
* **One `Request` per outbound message** is the container: `raw_text` = a templated one-line summary ("Quote request from saved quote <id>, supplier <merchant>"), `quantity` unset, state machine unchanged. A request for an aggregated message has N lines recorded in the `quote_rfq.linked` event payload (`quote_id`, `quote_version`, `line_ids`, `mode`, `mime_hash`), not in new `Request` fields. `per_item` creates one request/RFQ per line; `per_supplier` one per supplier. Both cover exactly the same line ids (as `rfq_messages` already guarantees).
* **One `RFQ` per message** with `candidate_mpns = ()`, `subject`/`body` = the rendered template output (body WITHOUT footer, as `RFQ.body` already says). Business identity block, footer and `mime_hash` come from the existing `SendService.prepare`, unchanged. No URL, no model text: the templates are the only text source and the renderer's checks run before anything is stored.
* **Approval** is the existing `approve_send(rfq_id, mime_hash)`: per-message `Approval` bound to the hash, kill switch, suppression and verification re-checks all unchanged. "Pending approval" means "prepared, unsent, held by the service".
* **Events** (rule 6): `rfq.prepared` is appended by the existing prepare path; the request moves `SPEC_CONFIRMED -> RFQ_DRAFTED` through `Workflow`. The quote link is recorded with an additional `quote_rfq.linked` event through the same event log (never a direct status write).
* **Tenant isolation** (rule 7): the quote snapshot is read through the tenant-scoped `QuoteService.get_quote(ctx, id)` (404 for another tenant), everything else through `TenantStore`.
* **Routes** (new `apps/api/quote_rfq_routes.py`): `POST /v1/quotes/{id}/rfq-drafts` `{mode, merchant_ids?}` (buyer+, extra fields refused) calls the new service method and returns the `PreparedRFQ` list awaiting approval; `GET /v1/quotes/{id}/rfq-drafts` is read-only (`list_prepared_rfqs`). The route holds no mail credentials and imports nothing from `send_service`; sending stays `POST /v1/rfqs/{rfq_id}/approve-send`.

## What blocks it (written to CONTRACT_CHANGES.md)
A public method on `PurchasingService` (and `PurchasingServicePort`) that accepts a templated message, e.g. `prepare_text_rfq(ctx, *, vendor_id, subject, body, line_refs, quote_ref)`. It must create the request container and RFQ itself through `_move`/`Workflow`, re-run the plain-text/link/markup check on subject and body (defence in depth, because the service must not trust its caller's text), apply `_business_identity`, `check_supplier_guards`, the vendor limits and `_check_messages`, and reuse `_prepare_one`. It must not relax R2/R3: it carries no candidate part and so cannot be used for a PO (`create_po_draft` still needs a selected, approved Tier A quote). Until it exists, a route here could only fake the flow.

`domain.py` and `ports.py` need no change for this mapping; the lines of an aggregated message live in the event payload. If the owners prefer lines as typed data, a `RequestLine` record in `domain.py` would be the (optional) contract change.

## Tests to write once the method exists
`tests/api/test_quote_rfq.py` and `tests/pack/test_quote_rfq_flow.py`: aggregated default gives one pending message per supplier containing every line; `per_item` one per line; editing the text changes `mime_hash` so `approve_send` with the old hash is a 409 and no approval is issued; the recording transport stays empty until `approve_send`; tenant B gets 404 and an empty list for tenant A's drafts; a line with a URL or markup is refused with nothing stored; events appended and `EventLog.verify` true. All with FakeLLM and the recording transport.

## As built
* **Merchant to supplier mapping**: the price-book `merchant_id` IS the id of the tenant's own `Vendor` (read through the tenant-scoped repository). A merchant with no such vendor, or one that is not attested, suppressed, opted out, not preferred, individual-subscriber (unless enabled) or has a callback pending, is a 409 naming the merchant; the whole call is refused before anything is stored (every message passes `check_text_rfq` first). Limitation: the in-memory `Store` keeps vendor ids unique across tenants (the Postgres store keys them per tenant), so with the in-memory store two tenants cannot both hold a vendor with the same id. A dedicated external-reference field on `Vendor` would remove this; that is a `domain.py` change and is not proposed here.
* **Scope of lines**: the messages come from `price_books(quote_id)["rfq_messages"]`, which today groups only the quote's gap lines (merchants without a firm price), see pricebook.md section 6a.
* **Idempotence**: a repeat POST returns the drafts already waiting (same supplier, lines and mode) and adds none.
* **Defence in depth**: the service re-checks subject and body (no link, markup, entity or control character; length caps) even though the renderer already did.
