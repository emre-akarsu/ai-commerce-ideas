# ADR-011: Deployment profiles for configurable, multi-market deployments
**Status:** accepted (2026-10-02). **Context:** the founder will deploy many similar workflows (markets, verticals, customers). Jurisdiction-specific behaviour (currency, tax, language, working days, legal wording, retention, thresholds) was hard-coded for the US. **Decision:** introduce `aiplat.profile`: a typed, bounded, versioned configuration schema; layered resolution (platform defaults → `base` → profile chain → tenant overrides) into an immutable, hashed `ResolvedProfile` with per-key provenance; safety rules R1–R12 have no config keys and the schema rejects values that would weaken them; tenants may override only a whitelist; the profile id and digest are recorded on every audit event. Vertical variation stays in packs (`employees/<pack>`); jurisdiction in `profiles/`; customer settings in tenant overrides. **Consequences:** a new market is a profile plus localised research plus conformance tests, not a fork; US behaviour is preserved by the `us` profile; the digest makes config changes auditable. **Alternatives rejected:** per-market code branches (unmaintainable); unconstrained free-form config (can silently weaken controls); config in environment variables only (no layering, no provenance). See `docs/architecture/configurability.md`.
