# ADR-012: Composable workflows, capability contracts and industry packs
**Status:** proposed. **Context:** the platform will host many ideas as plug-in modules and many industry versions of the same workflow. Today a vertical is code (`employees/purchasing/graph.py` builds its graph by hand; `employees/refurb` is a separate plain-Python pack) and modules have no typed contract or composition check. ADR-011 already makes jurisdiction a profile. **Decision:** add four things, all outside the frozen `core/domain.py` and `ports.py`: (1) versioned capability contracts as Protocols in `packages/aiplat`; (2) a `module.yaml` manifest per module (provides, requires, effects, LLM role and tools, pack extension points, evals); (3) declarative workflow templates whose steps name capabilities and are bound to modules at composition time, compiled to LangGraph; (4) industry packs as validated data (taxonomy, work packages, gates, questions, attributes, prompts, seed, evals). A deployment is a workflow template, a pack, a profile and a tenant, resolved into an immutable `ResolvedComposition` with a digest recorded in every event. A composition linter (C1 to C9) and matching runtime checks keep R1 to R12; no pack key can override a hard rule. **Consequences:** most new industries become data; ideas plug in as modules; a template and pack can be swapped without code changes. Costs: contracts need upkeep and risk early freezing (mitigation: rule of three, version them), configuration can sprawl, and the saving is unmeasured. **Not decided:** the DSL syntax beyond the sketch in `docs/architecture/composability.md`, third-party module signing, and whether the intent graph uses LangGraph or plain Python at first.
