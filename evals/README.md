# evals

`python -m evals.run` (or `make eval`) runs the tiered-equivalence engine over `golden/*_dev.jsonl`
and prints per-tier counts, every false Tier A/B, a Wilson upper bound and a verdict.

**SYNTHETIC SMOKE SET - proves the pipeline, not product accuracy.** Every row in
`golden/bearings_dev.jsonl` is synthetic (`synthetic: true`), uses the invented SynthCo parts in
`packages/components/parts/equivalence/data/`, and was labelled by the author of the engine rules.
It is not a measurement of accuracy on real parts, real distributors or real buyers.

## Row format

`GoldenItem` (frozen contract, `components.core.domain`): `id, family, split, request_text,
candidate_mpn, expected_tier, critical_mismatch, synthetic, rationale`. `critical_mismatch` is true
when the label is Tier D (a critical attribute differs or is unknown), i.e. the candidate must not be
accepted as A/B. The runner turns `request_text` into attributes with the deterministic normaliser
and classifies `candidate_mpn` with `classify_offered`. Labels were written by hand from the rules,
not generated by running the engine.

## Verdict (spec §8)

| Verdict | Condition | Exit |
|---|---|---|
| FAIL | any false Tier A/B (engine A/B where the label is C/D), at any n; or, at n >= 189, Wilson upper bound > 2% | 1 |
| INSUFFICIENT_N | no false A/B but fewer than 189 engine-labelled Tier A/B items | 0 |
| PASS | no false A/B, n >= 189 and upper bound <= 2% | 0 |

n is the number of engine-labelled A/B items. 189 is the smallest n at which zero errors give a Wilson
95% upper bound of 2% (one error would need 280, two 361); below it the gate cannot pass even with no
errors, so the verdict is INSUFFICIENT_N. Because any false A/B fails outright, the practical pass is zero
errors in at least 189 items. Zero errors proves < 5% only at n = 59 and < 1% only at n = 299 (exact
one-sided bound).
INSUFFICIENT_N is the expected result on the synthetic set and is not a pass.

## What this cannot tell us

Coverage (only deep-groove bearings and V-belt seed rows, a handful of invented parts), distribution
shift across part families, real cross-reference data quality, photo/OCR inputs, `criticality`-flagged
requests (no field in `GoldenItem`; covered by unit tests instead), and label noise (single labeller,
no kappa). The runner only reads the `dev` split.

## Sealing mechanism (not implemented with real labels)

The sealed test set must never be committed here and no prompt or rule may be tuned on it.
Intended process, to be built when a real set exists:

1. Two blind experts label each item independently; disagreements adjudicated; kappa >= 0.8 recorded.
2. Stratify by tier x missing-attribute x input type, with near-miss pairs and a time split.
3. Store the file outside the repo (access-controlled bucket). Commit only a manifest: item count,
   SHA-256 of the file, labelling date and kappa. The runner would refuse a sealed file whose hash does
   not match the manifest.
4. Every sealed run is appended to a log (who, when, git SHA, hash); cap runs per month.
5. Any item that leaks into a prompt, rule or dev set is retired and replaced.

`evals/run.py` deliberately rejects non-`dev` rows.
